# AI-assisted development framework (Fusion Practices)

How this project is built. Client-facing methodology document.

## The flow

```
Requirement
    │
    ▼
Research                 — read .context/, ADRs, open questions, PARKED_PLANS
    │
    ▼
Challenge                — does this fit the roadmap? does it conflict with an ADR?
    │
    ▼
Plan                     — phases, Done-when per phase, reversibility per phase,
    │                       deferred list, BE-*/FE-* task ids, new ADRs named
    ▼
Isolate                  — git worktree + DB copy. The live dev DB is never touched.
    │
    ▼
Build inside agent       — engineer agent writes code against the plan,
    boundaries              one phase at a time, in its own worktree
    │
    ▼
Independent review       — a second agent (or a human reviewer) checks
    │                       the diff against the plan. Not self-review.
    ▼
Build / typecheck /      — the loop that proves it compiles and the schema moves
    migration round trip
    │
    ▼
Machine regression       — full pytest suite + tsc. The number must be the number
    │                       before + the number of new tests. No skipped failures.
    ▼
Human testing            — click the thing. Does it do what the requirement said?
    │
    ▼
End-to-end               — the whole user journey, not just the new page.
    │                       (A new ticket flow is tested from inbox → book → evidence.)
    ▼
Scenario testing         — the awkward ones. Four-eye paths where requester == signer.
    │                       Rate limits. Invalid tokens. Concurrent writes.
    ▼
Record decisions         — one ADR per non-obvious choice. A short JSON file in
                            .context/decisions/, numbered next-in-sequence.
```

Nothing is skipped. If a phase doesn't need something (an architecture-only phase has no code to review), it's named and skipped in the plan, not silently dropped.

## The three agents and their boundaries

See `.claude/agents/`.

- **solution-architect** — plans, ADRs, Done-when verification. Reads code; never writes it.
- **backend-engineer** — services, repos, migrations, pytest. Reports done; never ticks the plan.
- **frontend-engineer** — Next.js pages, lib/api.ts, tsc. Reports done; never ticks the plan.

The architect is the plan's owner. The engineers are the plan's executors. **Separation of plan and build is a control, not an inconvenience.**

## Design constraints

- **Reversibility (D-02)** — every change has an off switch. A tested migration downgrade; a settings flag; an additive-not-destructive schema change.
- **Isolation (D-03)** — feature work is in a worktree against a DB copy. The live dev DB stays untouched. See ADR-0021.
- **Tenant isolation** — every operational table has `tenant_id`; every service query filters by it. Row-level security in Postgres is a parked plan (PHASE_2_MULTITENANCY_PLAN.md) that unparks only when customer #2 signs; until then the application-layer filter is the only line of defence and the four-eye controls on sensitive grants (ADR-0015) are the compensating control.
- **Additive, never destructive (D-01)** — forward migrations do not DROP. If you must, write an ADR explaining why.
- **Fail-closed authorization (D-04)** — a request with no matching permission is denied. Row scoping is a repo-layer filter derived from the principal; it is not a URL parameter the caller can tweak.

## What the client gets (not raw prompts)

- The methodology document (this file).
- The live architecture — `.context/architecture.json`, `.context/data-model.json`, `.context/api.json`, auto-regenerated by `python .context/update.py`.
- The decision log — 20+ ADRs under `.context/decisions/`, each tying a rule to the context that forced it.
- Phase-wise plans — `PHASE_2_BLUEPRINT.md`, `PHASE_2_IMPLEMENTATION_PLAN.md`, `PHASE_2_ADMIN_UI_PLAN.md`, `PHASE_2_MULTITENANCY_PLAN.md`. Parked plans are enforced by CI (`PARKED_PLANS.json` + `backend/tests/test_parked_plans.py`).
- The git log — every change references the ADR + roadmap id it closes.
- Scenario testing results — in `backend/tests/` (300+ tests, including control-loop and compliance e2e suites).

What the client does not get: a dump of chat transcripts. The transcript is a working surface; the deliverables above are the signed-off record.

## Why this works

- The **plan is reviewable before any code lands**. The expensive mistakes are architectural; catching them in the plan costs minutes, catching them at merge costs days.
- The **ADR is the memory**. Six months later nobody has to reconstruct "why did we do it this way?" — the ADR records the context and the decision in one place.
- The **context matrix is 50 KB, the code is megabytes**. A new session reads the matrix in seconds and acts correctly; reading the whole code first is both slower and less accurate (code moves; the matrix is updated per change).
- The **parked-plans guard is CI-enforced**. A plan parked because the business case isn't ready cannot sneak into main as a side effect of unrelated work. The park state is a tripwire, not a note.

## When this framework does NOT apply

- A one-line typo fix in a comment. Write the fix. Ship it.
- An ADR-level question with no code (e.g. "should we add a column?"). The architect answers in an ADR; no engineer agent needs to run.
- An operational task (provision a database, rotate a secret) with no code change. Record it in `.context/changes/YYYY-MM-DD.json` under `operational_followups` and move on.

Everything else goes through the flow.
